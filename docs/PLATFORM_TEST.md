# 飞白 平台手测清单（Windows · Tauri WebView2 · Release 验收关卡）

> 本清单是 **release 阻塞关卡**：全部勾选项在实机上通过后才允许发布。
>
> **Chromium E2E 全绿不得冒充 WebView2 实机通过。** E2E 跑在 Vite dev server + Playwright Chromium 上，`tauriBridge` 为 null，不接触 Tauri IPC、真实文件系统、原生对话框、文件关联与 WebView2 运行时——它验证的是编辑器逻辑，不是桌面壳。
>
> 必须在 **release 构建产物** 上执行（`npm run tauri:build` 生成的安装包，或与 release 同配置的本地产物）；`npm run dev` 的 Vite 页面结果无效。

## 准备

- 环境：Windows 10/11 x64；WebView2 Runtime（Win11 自带，Win10 需手动安装）；建议干净虚拟机或干净用户账户。
- 构建并安装：`npm ci && npm run tauri:build` → 安装 `src-tauri/target/release/bundle/nsis/飞白_*_x64-setup.exe`（或 MSI）。
- 拼写检查项需要英文词典：系统设置 → 语言 → 添加"英语（美国）"语言包（或用英文系统）。
- 测试夹具（建议放在独立目录，如 `C:\inkwhite-manual\fixtures\`）：
  - 正常 UTF-8 `.md` 若干（含中文标题与正文）
  - GBK（ANSI）编码 `.md` 一个：记事本保存时选"ANSI"编码写入中文
  - 损坏 UTF-8 `.md` 一个：用十六进制编辑器截断文件或在文件中部插入非法字节
  - 长文档 `.md`：含表格、长代码块、mermaid 图、KaTeX 公式、本地图片
  - 图片若干（png / jpg）
- 记录规则：失败项写明复现步骤并截图，作为 blocking 缺陷提交；通过项保持勾选，结论随 release notes 归档。

## 1. 文件关联 / 命令行打开

> 自动化无法覆盖的原因：E2E 运行在 Vite + Chromium 上（tauriBridge 为 null），没有安装包、注册表文件关联与 Shell 调用链；Rust 单测只覆盖参数提取与读取逻辑，无法验证 Windows 外壳（双击 / 打开方式 / 多选）的真实调用序列，也无法验证单实例转发与 PendingOpen 的时序。

- [ ] 安装后检查 `.md` / `.markdown` / `.txt` 文件的图标与右键"打开方式"列表 —— 期望：图标正确，"打开方式"中包含 飞白。
- [ ] 应用未启动时双击一个 `.md` —— 期望：应用启动并打开该文件（标题/状态栏显示文件名，内容渲染正确）。
- [ ] 应用已运行时双击另一个 `.md` —— 期望：不新开进程，已运行窗口聚焦并打开新文件（单实例锁）。
- [ ] 多选多个 `.md` 后右键"打开方式 → 飞白" —— 期望：每个文件都被接收并逐个打开（PendingOpen 队列/事件按序消费），最终显示最后一个文件，无崩溃、无重复窗口。
- [ ] 用 PowerShell 执行 `飞白.exe <path.md>` —— 期望：与双击行为一致（首实例打开 / 次实例转发给已运行实例）。
- [ ] 打开 GBK 编码的 `.md` —— 期望：出现明确的错误提示（如"无法读取文件：编码不支持"），不清空当前编辑内容，不崩溃。
- [ ] 打开损坏 UTF-8（含非法字节）的 `.md` —— 期望：同样出现明确错误提示，而不是静默失败或把乱码写进编辑器。

## 2. 拖放

> 自动化无法覆盖的原因：Playwright 只能构造 `DataTransfer` 对象，与真实 OS 拖放（Shell 拖拽、跨盘符、图片落盘）路径完全不同；且 E2E 环境 tauriBridge 为 null，没有真实文件系统写入。Rust 侧也无拖放路径可单测。

- [ ] 从资源管理器把 `.md` 拖入窗口 —— 期望：文件被打开（与"打开"对话框行为一致），窗口不导航。
- [ ] 把图片（png/jpg）拖入编辑区 —— 期望：图片落盘（保存到文档同目录），并在原文插入 Markdown 图片引用。
- [ ] 未命名文档（尚未另存为）时拖入图片/文件 —— 期望：先弹出"另存为"选择，取消则放弃，不产生半落盘文件。
- [ ] 跨盘符拖放（如从 D: 盘拖入打开在 C: 盘的文档）—— 期望：落盘/打开成功，无权限错误。
- [ ] 拖放完成后检查应用状态 —— 期望：webview 未发生导航（URL 不变、编辑内容与光标不丢、无整页变成文件内容的现象）。

## 3. 外链

> 自动化无法覆盖的原因：E2E fixture 屏蔽了所有外网请求（route abort），无法验证"系统浏览器打开"；WebView2 的 `window.open` 行为与 Playwright 的 Chromium 上下文不同，且无法断言应用窗口未跳转、编辑状态未丢失。

- [ ] 在预览中点击 `https://` 外链 —— 期望：系统默认浏览器打开该 URL。
- [ ] 点击外链后回到应用 —— 期望：应用窗口未跳转、未新建空白窗口，编辑内容、光标位置与未保存改动全部保留。
- [ ] 构造危险链接（`[x](javascript:alert(1))`、`data:`、`file:`）并点击 —— 期望：被拒绝（不执行脚本、不导航、无弹窗）。
- [ ] 点击页内锚点链接（`#标题`）—— 期望：仍在应用内平滑滚动到对应标题，不触发外部行为。
- [ ] 点击无法解析的链接（如 `[x](http://[`）—— 期望：状态栏出现"无法打开链接"提示，无崩溃。

## 4. 关闭确认与窗口状态

> 自动化无法覆盖的原因：原生窗口管理器事件（标题栏 ×、Alt+F4、菜单"关闭窗口"、进程终止与重启）无法由 Playwright 驱动；窗口位置/尺寸持久化涉及 Tauri 窗口生命周期，headless 环境不可验证。

- [ ] dirty 状态（有未保存改动）点标题栏 × —— 期望：出现关闭确认（提示未保存），选取消则窗口不关、内容保留。
- [ ] dirty 状态按 Alt+F4 —— 期望：同样出现确认，取消不关。
- [ ] dirty 状态用菜单"文件 → 关闭窗口" —— 期望：同样出现确认。
- [ ] 确认关闭后重新启动 —— 期望：草稿内容恢复（localStorage 兜底），之前打开的本地文件关联恢复。
- [ ] 干净状态（无未保存改动）关闭 —— 期望：直接退出，无确认打扰。
- [ ] 调整窗口位置与大小后退出再启动 —— 期望：位置与尺寸恢复；多显示器布局变化时窗口至少不跑出可视区域。

## 5. 拼写检查

> 自动化无法覆盖的原因：波浪线与右键建议来自 WebView2 调用操作系统词典服务（语言包），headless Chromium 没有词典上下文，也无法断言右键菜单中的"拼写建议"项。

- [ ] 在英文词典环境（已装英语语言包）下，编辑区输入拼错的英文词（如 "helo"）—— 期望：出现红色波浪线。
- [ ] 右键该词 —— 期望：菜单出现拼写建议（如 "hello"），点击后替换成功。
- [ ] 输入正确的英文与中文 —— 期望：无波浪线误报。
- [ ] 批注输入框与预览区 —— 期望：行为与设计一致（不出现波浪线或与编辑区行为相同）。

## 6. PDF 打印

> 自动化无法覆盖的原因：`window.print()` 走 WebView2 打印子系统与系统打印对话框；E2E 只能断言页面内容，无法产出真实 PDF，也无法验证"可选字 / 可搜索 / 分页合理"，字体与打印驱动行为与 headless 输出不等价。

- [ ] 打开含表格、代码块、图片、KaTeX 公式、mermaid 图的长文档，按 Ctrl+P / 打印 —— 期望：出现打印对话框，默认打印机可选"Microsoft Print to PDF"。
- [ ] 另存为 PDF 后用阅读器打开 —— 期望：文字可选中、可搜索（不是整页位图）。
- [ ] 分页检查 —— 期望：表格、代码块、图、公式不被截断（break-inside: avoid 生效），页边距约 0.5cm，无编辑器 UI（工具栏/面板）混入打印内容。
- [ ] 暗色纸 / 暗主题下打印 —— 期望：对比度可读（print-color-adjust: exact 生效），文字不淡到看不见。
- [ ] 打印完成后回到应用 —— 期望：无崩溃、无导航，编辑内容保留。

## 7. Word / WPS 兼容

> 自动化无法覆盖的原因：第三方应用互操作（编码识别、换行、字体回退）依赖真实安装的 Word / WPS，无法在 CI 中驱动。

- [ ] 用 飞白 另存为/保存一个含中文的 `.md` —— 期望：用 Word 打开该文件，中文无乱码、内容完整。
- [ ] 同一文件用 WPS 打开 —— 期望：内容完整可读，Markdown 文本结构（标题/列表/表格源码）未损坏。
- [ ] 该文件再用记事本 / VS Code 打开 —— 期望：仍是正常 UTF-8，无 BOM 垃圾字符，内容未被改写。

## 8. 文件监听（外部修改）

> 自动化无法覆盖的原因：notify crate 的事件时序与"编辑器自写回不触发冲突提示"依赖真实文件系统事件序列；Playwright 环境 tauriBridge 为 null，Rust 单测只能验证逻辑分支，无法模拟 OS 事件流。

- [ ] 打开本地 `.md`，用记事本 / VS Code 修改并保存 —— 期望：编辑器提示文件已被外部修改，未编辑状态下自动重载新内容。
- [ ] 编辑器有未保存改动时外部修改文件 —— 期望：进入冲突状态（提示"Ctrl+S 保存将覆盖对方改动"），不自动覆盖、不丢失任何一方内容。
- [ ] 冲突后在编辑器按 Ctrl+S 保存（写回）—— 期望：不出现重复冲突提示（watcher 收到自身写回事件被基线更新/去抖吸收）。
- [ ] 外部修改后把焦点切回应用窗口 —— 期望：窗口聚焦时补查一次（焦点检查兜底），内容同步。
- [ ] 打开的文件被外部删除/移动 —— 期望：不崩溃，编辑器内容保留，同步安静停止或给出提示。

## 9. 长图导出（WebView2 兼容）

> 自动化无法覆盖的原因：E2E（`tests/e2e/longImage.spec.ts`）只在 Chromium 验证生成逻辑，但 WebView2 的字体栈、SVG foreignObject 光栅化与画布内存上限与 Chromium 构建不同，切片拼接质量只能实机目检。

- [ ] 打开含表格、代码、mermaid 图、KaTeX 公式、图片的文档，执行"保存长图" —— 期望：生成的 PNG 所有元素完整、不裁切、不错位。
- [ ] 超一屏的长文档（触发分片拼接）—— 期望：切片边界无白缝、无错位、无重复行。
- [ ] 亮纸与暗纸各导出一张 —— 期望：纸色、字体与预览一致（跟随预览主题）。
- [ ] 导出 PNG 用系统查看器打开 —— 期望：尺寸合理、可正常打开；超长文档超出编码上限时应给出明确提示，而非静默失败。

## 10. 文件树

> 自动化无法覆盖的原因：原生目录选择对话框只能人工操作；"未授权目录不可枚举"虽有 Rust 单测覆盖 IPC 层，但"对话框授权 → 树浏览 → 节点打开 → 重启后授权/根记忆恢复"的端到端链路必须实机验证。

- [ ] 打开文件树并选择根目录 —— 期望：出现原生目录对话框，选择后树列出该目录（目录在前、文件在后、按名称不区分大小写排序）。
- [ ] 展开 / 折叠子目录 —— 期望：逐级展开正常，深层目录可浏览。
- [ ] 点击树中 `.md` 节点 —— 期望：文件被打开，标题 / 状态栏更新。
- [ ] 重启应用后再打开文件树 —— 期望：上次选择的根目录被记忆恢复（localStorage 根记忆）。
- [ ] 未授权目录不可枚举 —— 期望：未经过目录对话框授权的路径（如开发者工具中直接调用 list_directory 指向其他目录）被拒绝（报错或空结果），不泄漏目录内容。
